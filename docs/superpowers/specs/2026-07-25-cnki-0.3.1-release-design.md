# CNKI Skill 0.3.1 发布设计

## 目标

以远程 `main` 当前提交为基准发布 `v0.3.1`，保留现有 `v0.3.0` 标签和 Release，不覆盖、不移动、不删除其附件。

## 版本契约

以下位置统一使用 `0.3.1`：

- `top-journal-search-lists/scripts/cnki_search/__init__.py`
- `top-journal-search-lists/mcpb/src/cnki_search/__init__.py`
- `top-journal-search-lists/mcpb/pyproject.toml`
- `top-journal-search-lists/mcpb/manifest.json`
- `top-journal-search-lists/mcpb/uv.lock` 中 `cnki-search-mcp` 项目版本

MCP `serverInfo.version` 继续读取 `cnki_search.__version__`，不单独维护版本常量。

## 正式构建环境

GitHub Actions 继续在 Ubuntu、Windows 和 macOS 上运行测试、目录校验、MCP 握手、安装器验证和构建检查。只有 Ubuntu 3.11 作业上传正式发布附件，名称固定为 `release-canonical-ubuntu-py3.11`。

Windows、macOS 和 Ubuntu 3.12 至 3.14 不上传发布附件，避免同一版本出现不同平台生成的 ZIP 字节差异。

正式附件固定为：

- `top-journal-search-lists_Skill.zip`
- `cnki-search.mcpb`
- `checksums.sha256`

## 发布流程

1. 在独立分支完成版本和 CI 契约修改。
2. 本地运行全量 pytest、ruff、mypy、目录校验、MCP 握手和两次可重复构建。
3. 推送分支并创建面向 `main` 的 PR。
4. 远程 CI 全部通过后合并 PR。
5. 等待合并提交触发的 `main` CI 全部通过。
6. 从该次 `main` CI 下载 `release-canonical-ubuntu-py3.11`。
7. 核对附件内校验和后，在合并提交创建 `v0.3.1` 标签和正式 Release。
8. 发布后再次核验 `v0.3.0` 的标签目标和附件摘要未发生变化。

## 失败处理

- 任一测试、静态检查、握手或构建失败时停止发布，不创建标签。
- `main` 在 PR 合并后发生新的提交时，不使用旧 CI 产物；必须重新以最新 `main` 运行并取件。
- 附件缺失、校验和不匹配或来源不是 Ubuntu 3.11 时，不创建 Release。
- 如果 `v0.3.1` 标签或 Release 已存在，则停止并核查，不覆盖现有对象。

## 验收标准

- 五处版本来源均为 `0.3.1`。
- CI 中只有一个上传正式发布附件的步骤。
- 正式附件来自 Ubuntu 3.11。
- PR 和合并后的 `main` CI 均全部通过。
- `v0.3.1` 标签精确指向通过 CI 的 `main` 合并提交。
- Release 三个附件的 GitHub 摘要与下载后本地 SHA256 一致。
- `v0.3.0` 标签目标和三个附件摘要保持不变。
